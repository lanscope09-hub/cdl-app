② 五大決勝分水嶺（最高頻）

CDL 的陷阱幾乎都是「兩個產品看起來都對」。每一組都有唯一的分水嶺，記分水嶺比記產品有用。

1. 碰不碰 OS？
要碰／要裝驅動／full control → Compute Engine　｜　不想碰／fully managed → 往 Cloud Run、App Engine 走
2. 交出的是 code 還是 container？
交程式碼 → App Engine（web app）、Cloud Functions（一段函式）
交容器 → Cloud Run（一個）、GKE（一群）
3. 一個容器還是一群容器？
一個貨櫃叫 Uber → Cloud Run　｜　一座港口要塔台調度（Kubernetes / orchestration / microservices）→ GKE
⚠️ 看到 container 別反射選 Cloud Run，要再看「一個 vs 一群」
4. 誰管 node？
自己管 → GKE Standard　｜　without managing nodes → GKE Autopilot
5. 事件觸發還是常駐服務？
triggered when X happens / event-driven → Cloud Functions　｜　接請求、開服務 → Cloud Run
⚠️ 兩者都會出現 serverless、pay only when running，那些字切不開它們
收尾口訣：碰硬體找包場，碰 OS 找 CE，塔台管群不管台（Autopilot 連台都不管），廚房只收食譜還會試吃分流（App Engine），門鈴有事才叮咚（Functions）。

③ 資料庫五顆（最好拿分）

產品一句話觸發字
Cloud Spanner全球關聯式 + 強一致global、ACID、strong consistency、跨國金融交易、unlimited scale
Cloud SQL老牌關聯式搬上雲MySQL、PostgreSQL、migrate、single region
BigQuery資料倉儲，SQL 分析data warehouse、analytics、pay per query、報表 BI
BigtableNoSQL，收海量即時資料IoT、time-series、low latency、millions of devices
Firestore行動 App 後端mobile app backend、flexible schema、sync to devices

三組必考陷阱

Cloud SQL vs Spanner（都是 SQL）
單區域、MySQL/PostgreSQL、一般規模 → Cloud SQL
全球、ACID、無限擴展 → Spanner
Bigtable vs BigQuery（名字超像，其實無關）
Bigtable 收資料，BigQuery 分析資料。兩件事，不是兩步驟。
⚠️ 它們沒有先後或依賴關係，別記成「先 Bigtable 才能 BigQuery」
Spanner vs Firestore（都講「即時同步」）
有 no errors / guarantee / ACID / 交易 / SQL / global → Spanner
有 mobile app / flexible schema / sync to devices → Firestore
⚠️ real-time sync 是 Firestore 的誘餌字，要找「保證」級的字才是 Spanner

⑤ AI / ML 四層 + 三輔助

核心問題只有一個：這個團隊有多少 ML 能力、想不想自己訓練模型？
層級什麼時候選它觸發字
預訓練 API標準任務、要快、沒有 ML 人力pre-trained、no data science expertise、as quickly as possible
AutoML要用自己的資料做客製模型，但不想寫 codecustom model、your own data、no code、labeled data
Vertex AI 自訂訓練有資料科學團隊，要完全控制data science team、full control、TensorFlow、hyperparameters
BigQuery ML資料已在 BigQuery，用 SQL 就想做data already in BigQuery、SQL、analyst（非 data scientist）
兩個已驗證的陷阱：
① 題目提到 machine learning 不代表答案是 AutoML／Vertex AI。標準辨識任務 + 想快速整合 → 仍然是預訓練 API。
② 「資料在 BigQuery」不是決勝字。要 TensorFlow 客製 + 完全控制 → 仍然是 Vertex AI 自訂訓練。

三個獨立專才（不套四層架構）

有對話互動 → Dialogflow（chatbot、virtual agent）
有文件要抽欄位 → Document AI（extract data from forms、KYC）
要生出全新內容 → Gemini / 生成式 AI（generate、create，不只是分類）

⑥ 安全維運（配分最重的一塊）

IAM 三種角色

Basic RoleOwner/Editor/Viewer，範圍大、老派 broad、legacy
Predefined RoleGoogle 切好的精細包 fine-grained、specific service
Custom RoleGoogle 沒有現成組合剛好符合時才自己拼
・audit / external auditor 出現 → 給最小夠用角色（例如 Storage Object Viewer），不是 Owner/Editor
・Predefined vs Custom 的分水嶺不是「specific」這個字，是「Google 有沒有現成的剛好符合」
・Custom Role 不會用久了變成 Predefined，兩者是平行系統
・給程式／機器用的身分 = Service Account（沒有人類登入）
・一群人共用權限、新人自動繼承 = Google Group

資源階層（反直覺，必背）

Organization → Folder → Project → Resource
政策由上往下繼承且疊加（inherit、additive）——越往下只會越多，不會越少。
⚠️ 反直覺陷阱：不是「層級越細優先權越大」，下層無法用一般 IAM 收回上層給的權限。
環境隔離（dev / staging / prod）要用獨立 Project。
・不是 label（label 不提供邊界，只是標籤）
・不是 Folder（Folder 是分組容器，Project 才是計費邊界）

共同責任模型

Security OF the Cloud（機房、硬體）→ 永遠 Google 負責
Security IN the Cloud（資料、存取）→ 永遠 客戶 負責

IaaS 客戶顧 OS + 防火牆 + 資料｜PaaS 只顧程式碼 + 資料｜SaaS 主要顧「誰能存取」
通則：不管哪一層，「誰能存取資料」永遠是客戶的責任。

加密

at rest（靜態）與 in transit（傳輸中）→ Google 預設自動加密，客戶不用設定
CMEK：客戶管金鑰規則與輪替，Google 仍負責實際加解密
CSEK：客戶每次自己提供鑰匙，Google 完全不存，鑰匙掉了資料救不回
決勝句：題幹說「Google 還在幫忙做加解密」→ CMEK；「Google 完全不留鑰匙」→ CSEK

監控 vs 日誌

Cloud Monitoring = 看數字（metrics、dashboard、uptime check）
Cloud Logging = 看紀錄（events as text、troubleshooting、audit trail）

SLA / SLO / SLI 三兄弟

SLI = 量測出來的實際數字（measured、actual）
SLO = 內部設定的目標（internal target）
SLA = 對外合約承諾，沒達標要賠錢（contract、penalty）
Error Budget = SLO 允許失敗的額度，還沒用完可以衝新功能，快用完轉守
⚠️ 陷阱：題目可能只描述定義（如「還剩多少失敗容許空間」）而不點名詞彙，要能反應過來

支援方案

Basic（免費，無回應保證）＜ Standard（工作時間）＜ Enhanced（24/7）＜ Premium
只有 Premium 配 Technical Account Manager（TAM） — 這是最明確的單一識別特徵，看到 TAM 直接選 Premium。

⑨ 網路（考點集中在「怎麼連」）

地端連上雲的四種路

方案什麼時候選觸發字
Dedicated Interconnect不可走公網、要 SLA、頻寬大，直連 Googlededicated connection、not over public internet、SLA
Partner Interconnect同上，但透過電信商轉接（自家機房離 Google 太遠）through a service provider / partner
Cloud VPN走公網但加密，要馬上通、頻寬需求不大quickly、encrypted tunnel、over the internet、IPsec
Direct / Carrier Peering只是要接觸 Google 公開服務，不進 VPCpeering
分水嶺：看「時間急不急」——要馬上通 → Cloud VPN；要高頻寬 + SLA、可以等 → Interconnect。

VPC 相關

Shared VPC → 同一個組織內多專案共用同一張網路
VPC Peering → 跨組織／跨專案互連兩張獨立的網路
Private Google Access → VM 沒有外部 IP，但要連 Google 服務（是「網路路徑」層設定）
Cloud NAT → VM 要連外部網際網路（下載更新等），但不想給它公開 IP

防護與流量

Cloud Armor → 擋 DDoS 與網頁攻擊（第 7 層），搭全球外部 HTTP(S) 負載平衡器
Firewall rules → 題幹出現 enter and leave the network（進出網路）
IAM / 2SV → 題幹講的是身分驗證而非流量
Cloud CDN → 靜態內容快取到離使用者近的地方
Cloud DNS → 網域名稱解析
延遲與容錯的差別（常混）：
跨洲延遲高 → 在使用者所在的 region 建複本
同區容錯 → 跨多個 zone 部署
region = 地理區域（台灣、東京）；zone = 同一區域內的獨立機房

⑩ 維運監控 + SRE 文化

Operations Suite 五件套（誰看什麼）

工具看什麼觸發字
Cloud Monitoring數字指標metrics、dashboards、uptime check
Cloud Logging文字事件紀錄events、logs、audit trail、troubleshooting
Cloud Trace請求走過哪些服務、卡在哪latency、request path、distributed tracing
Cloud Profiler程式吃了多少 CPU / 記憶體CPU、memory consumption
Error Reporting把錯誤自動歸類、通知errors grouped、alerts
・題目要「一站式維運工具」→ Google Cloud Operations Suite（整套的名字）
・出現 latency 或「請求走了哪些服務」→ Cloud Trace，不要選加 log
・跨多服務找「卡在哪一段」→ Trace；看單一服務「發生了什麼」→ Logging
・Cloud Debugger = 在正式環境「看」變數狀態，不停機、不改程式。凡是敘述「要改程式重新部署」的一律錯

SRE / DevOps 文化題（常考觀念，不考工具）

toil（苦工） = 重複的人工作業。自動化的首要目標就是消除 toil
blameless postmortem（無咎責檢討） = 對事不對人，失敗是學習資料不是懲罰理由
measure everything 指的是系統的可靠度與健康（SLI/SLO），不是人的感受或財務數字
⚠️ 選項只要出現 blame（責備）、懲處、究責 → 幾乎一定是錯的

Error Budget 怎麼用

SLO 達標且錯誤預算還有餘 → 可以放膽發新版、衝創新
SLO 沒達成 → 凍結新功能，先修穩定性
⚠️ error budget 是自己內部 SLO 的餘裕；SLA 沒達成是對外賠錢。兩件事別混。

產品生命週期（合規題會用）

Preview / Alpha / Beta（沒有 SLA）→ GA（有 SLA）→ Deprecated（SLA 到期前仍有效）
合規／正式環境的題目只收有 SLA 的版本，看到 Beta 就淘汰

備份 vs 備援（字面很像，考點不同）

題幹出現 restore 還原 / recover 復原 → backup 備份
題幹出現 avoid single point of failure 避免單點故障 → redundancy 備援
災難復原三原則：備份要異地、要定期演練還原、單一地點的備份不算備援

⑪ 成本管理

方案什麼時候選
CUD 承諾折扣用量穩定可預測且 ≥ 1 年（1 年或 3 年）
SUD 持續使用折扣自動累積，不用承諾，折扣較小
Spot / Preemptible可被中斷的批次工作，最便宜
隨用隨付短期、臨時、無法預測
Reservations 預留要「保證拿得到容量」（與折扣是兩件事，可併用）
・要省錢 → CUD（承諾折扣）；要保證有機器可用 → Reservations（預留）。這兩個常被混在同一題裡
・看到 across all projects（跨專案）+ easily → CUD discount sharing（折扣共用）；逐專案設定的選項一律排除

BigQuery 計費三種

偶爾查 → On-demand（依掃描量計費）
長期穩定大量 → 固定費率／預留 slots
短時間爆量 → Flex Slots

成本觀念題

CapEx → OpEx：上雲把「一次買斷硬體」換成「按用量付費」。
⚠️ 選項若寫「把 pay-as-you-go 改成 capital expenditure」→ 方向相反，一律錯
TCO（總持有成本）= 全部成本，算它的目的是比較上雲划不划算
預算警示只會通知，不會自動停掉服務（常見陷阱）

⑫ 數位轉型與商業概念（79 題，題目最抽象）

雲端五大特徵

「多客戶共用」→ multi-tenancy
「按需伸縮」→ elasticity
「任何裝置連得上」→ broad network access
「自己開通不用等人」→ on-demand self-service
「用多少算多少」→ measured service

三種服務模型

想維持自己掌控底層 → IaaS　｜　不想管、想交出去 → PaaS / SaaS
跨章對照：Compute Engine（IaaS）→ App Engine / Cloud Run（PaaS）→ Workspace（SaaS）

部署模型

地端 + 公有雲並存 → hybrid 混合雲
兩家以上公有雲、沒提地端 → multi-cloud 多雲
「不想再管基礎設施」→ public cloud 公有雲
法規要求資料留地端／留境內 → 選「受管制的部分留地端 + 其餘上雲」（混合雲思維）
⚠️「全部不動」與「無視法規」永遠是錯的選項

Anthos 與 Apigee（這兩個很好認）

題目同時出現 consistent 與 multi-cloud / hybrid → Anthos
「不想被單一廠商綁 + 跨多雲 + 已在用容器」→ Anthos（只講「要跑容器」才選 GKE）

「把 API 開放給外部／合作夥伴、要收費、要控管流量」→ Apigee
⚠️ 看到 API 管理需求，不要選「自己寫程式」的選項

API 題的固定模式

只要題幹同時出現 existing / legacy（舊系統）與 new application（新應用）→ 答案永遠是「用 API 讓新舊互通」。
「舊系統不能動／沒預算改造，但要讓別人用到裡面的資料」→ 選 API；出現 Compute Engine、GKE、Anthos 這種要先搬遷的選項就淘汰。
看到 manually 手動、case-by-case 逐案 → 一定是錯的。

雲端成熟度四階（考過，要記順序）

tactical 戰術 → strategic 策略 → transformational 轉型
問「怎麼往上一級」→ 選帶 culture 文化、blameless 無責備、visibility 透明、programmatic 自動化 的選項
問 transformational 做法 → 選帶 culture、continuous 持續、shared 共享、peer 同儕 的
⚠️ 看到 isolated 孤立、blame 責備、one-off 一次性 → 淘汰

組織與文化題的固定答法

silos（孤島）題 → 選 shared goals 共同目標 / shared ownership 共同當責
痛點是 inflexible / rigid（僵化）→ 選「更容易嘗試、更快迭代」
痛點是「被限制」→ 選帶 innovate 創新、new tools 的
「什麼促成現代化決定」→ 答案幾乎都是「舊做法太慢／太貴／太僵化」
題幹有 automatically → 淘汰所有含 manually、self-assess 自評、visit 親自前往 的選項

代管服務自動包辦什麼

記三個：patching 修補、upgrades 升版、底層維運。
使用者權限、資料政策、成本決策 永遠是客戶自己的事（呼應共同責任模型）。

⑬ 答題模式與選項陷阱（不用背知識就能拿分）

這一章可能是全篇最划算的。
CDL 的錯誤選項有固定寫法，認出來就能先刪掉兩個。

看到就幾乎可以淘汰的字

選項裡出現為什麼錯
always / never / cannot / all of the time絕對字眼，雲端幾乎不做絕對承諾
100% availability一律錯。雲端只承諾 SLA 幾個 9，沒有 100%
manually / case-by-case題幹通常在問自動化，手動一定不是答案
blame / 究責 / 懲處SRE 文化題的反面，一律錯
「預算／成本不用擔心」上雲只是換一種花錢方式，不是不用錢
「自己保有硬體掌控」問「上雲好處」時，這方向就是錯的
pay-as-you-go → CapEx方向相反，上雲是 CapEx → OpEx

什麼時候選 All of the Above

選項 A/B/C 各講一項都成立的好處、彼此不衝突，而且有 All of the Above → 選它。
典型場景：問某產品（如 Anthos、Spanner）「有哪些能力」的列舉題。

複選題的處理

題幹寫 Select two / Choose two → 一定要選滿兩個，少選不給分。
